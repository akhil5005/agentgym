# Deploying AgentGym

Both services run on Render's free tier, driven by the `render.yaml` blueprint
in the repository root. No Docker, no Terraform, no AWS.

| Piece | Where | What it does |
| --- | --- | --- |
| Database | any Postgres — see step 1 | Holds tasks and episodes |
| Backend | `agentgym-api` on Render | FastAPI, stores and serves results |
| Frontend | `agentgym-web` on Render | The Next.js dashboard |

**The blueprint does not create the database.** Render allows only one active
free Postgres per account, so a blueprint that declares one fails the entire
apply for anyone who already has a free database — including with the rest of
the resources marked "canceled: another action failed". You bring a connection
string instead, which also means you can host the database anywhere.

**Episodes still run on your own machine.** Nothing you deploy ever executes
agent-written code — you run the episodes locally with the runner CLI and upload
the finished results. That split is the project's actual security boundary, so
do not try to "helpfully" move the runner onto the server.

> Render changes its dashboard and free-tier limits regularly. The steps below
> were accurate when written; if a screen does not match, check Render's own
> current docs rather than hunting for the button described here.

---

## 1. Get a Postgres connection string

You need one before applying the blueprint. Three ways, in the order worth
trying:

### Option A — a new free database elsewhere (recommended)

[Neon](https://neon.tech) and [Supabase](https://supabase.com) both give you a
free Postgres in about a minute. Create a project, copy the connection string.
Neon's looks like:

```
postgresql://user:password@ep-something-123456.us-east-2.aws.neon.tech/neondb?sslmode=require
```

This is the recommended option because AgentGym gets a database to itself, so
there is nothing to collide with. Treat the string as a password — it is one.

### Option B — reuse the free Postgres you already have on Render

Works, and keeps everything on one provider, but **check for table-name
collisions first.** AgentGym creates tables called `tasks`, `episodes` and
`steps`, and `create_all` silently skips a table that already exists — so if
another project owns a `tasks` table, this app will bind to it and fail later
with confusing errors rather than at startup.

Check before you commit to it:

```bash
psql "<your-existing-connection-string>" -c "\dt" | grep -E "tasks|episodes|steps"
```

No output means you are clear. Then copy the **Internal Database URL** from the
database's page — internal, not external, because the API runs on Render too,
so it should stay on the private network.

### Option C — no database at all

Leave `DATABASE_URL` blank and the app falls back to SQLite on local disk. On a
free Render service that disk is ephemeral: every sleep and every redeploy
wipes it, so the dashboard empties out on its own. Fine for a five-minute smoke
test, useless for showing anyone.

## 2. Apply the blueprint

1. Push this repository to GitHub (Render reads the blueprint from the repo).
2. In Render, choose **New → Blueprint** and pick the repository.
3. Render reads `render.yaml`, shows the two services it is about to create,
   and asks for the three values marked `sync: false`:

   | Prompt | Answer |
   | --- | --- |
   | `DATABASE_URL` (on `agentgym-api`) | the connection string from step 1 |
   | `FRONTEND_ORIGIN` (on `agentgym-api`) | `https://agentgym-web.onrender.com` |
   | `NEXT_PUBLIC_API_URL` (on `agentgym-web`) | `https://agentgym-api.onrender.com` |

   No trailing slashes on the URLs. If Render says a service name is taken it
   appends a suffix — use the name it actually assigned and set the other
   service's variable to match, or the browser will hit a CORS error.

4. Click **Apply**. The first build takes a few minutes.

The rest is wired up for you:

- `INGEST_API_KEY` is generated by Render (`generateValue: true`), so the
  upload key is never written down in this repository.
- `ENV=prod`, which makes the backend **refuse to start** if `INGEST_API_KEY`
  is still the default `dev-key`. That is deliberate: failing loudly at startup
  beats running with a publicly known key.
- `PYTHON_VERSION` and `NODE_VERSION` are pinned, so Render does not pick a
  default older than this project needs.

You do not need to create any tables. The backend creates them on startup.

### Check it

```bash
curl https://agentgym-api.onrender.com/api/health
# {"status":"ok"}
```

`https://agentgym-api.onrender.com/docs` serves the generated API docs, and
`https://agentgym-web.onrender.com` is the dashboard. It will be empty until
step 4.

---

## 3. Read the generated ingest key

Render made up `INGEST_API_KEY` and did not show it to you. To upload results
you need its value:

**Render → `agentgym-api` → Environment → `INGEST_API_KEY` → reveal.**

Treat it as a password. It is the only thing standing between your leaderboard
and anyone who finds the URL.

---

## 4. Upload your results

Everything above is empty until you send it some data. From your own machine,
in the repository root with the virtualenv active:

```bash
export AGENTGYM_API=https://agentgym-api.onrender.com
export AGENTGYM_KEY=the-value-you-just-revealed

# Task metadata first — episodes reference tasks, so this has to come first.
python -m agentgym.runner sync-tasks --api "$AGENTGYM_API" --key "$AGENTGYM_KEY"

# Then the results. These run locally and upload when each episode finishes.
python -m agentgym.runner run --agent oracle --tasks all --out runs/oracle.jsonl \
  --api "$AGENTGYM_API" --key "$AGENTGYM_KEY"
python -m agentgym.runner run --agent noop   --tasks all --out runs/noop.jsonl \
  --api "$AGENTGYM_API" --key "$AGENTGYM_KEY"
python -m agentgym.runner run --agent tamper --tasks all --out runs/tamper.jsonl \
  --api "$AGENTGYM_API" --key "$AGENTGYM_KEY"
```

On PowerShell, use `$env:AGENTGYM_API = "https://..."` instead of `export`.

Already have run files from an earlier local run? Upload those instead of
re-running anything:

```bash
python -m agentgym.runner upload "runs/*.jsonl" --api "$AGENTGYM_API" --key "$AGENTGYM_KEY"
```

If an upload fails partway — the free tier was asleep, the wifi dropped — the
run files are still on disk and re-uploading is safe. Episodes already stored
come back as "already present" rather than being duplicated, so you can run
that as many times as you like.

`sync-tasks` uploads only each task's id, title, difficulty, category,
description and step limit. **Hidden tests, reference solutions and the hidden
test count never leave your machine.** That is enforced in code by
`Task.public_dict()`, not by remembering to be careful.

## Free-tier limits worth knowing

These are the ones that will actually bite you:

| Limit | What happens |
| --- | --- |
| **A free Render Postgres expires 30 days after creation** | Render deletes it after a 14-day grace period, and your stored episodes go with it. Re-run step 4 against a fresh database, or pay for the database to keep it. Does not apply if you used Neon or Supabase in step 1 — neither expires on a timer. |
| Free web services sleep after ~15 minutes idle | The next request wakes the service and can take 30–60 seconds. That is why the dashboard shows a loading state rather than failing. |
| 750 free instance hours per month, shared across services | Two always-on free services would exceed this; the sleep behaviour above is what keeps you under it. |

If you used a free Render Postgres, **the 30-day expiry is the one that will
catch you out** on a project you are showing to someone. Whichever option you
chose, open the dashboard once before an interview to wake the services and
confirm the data is still there.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| Apply fails with "cannot have more than one active free tier database", everything else "canceled: another action failed" | An older version of `render.yaml` declared a `databases:` block and you already have a free Postgres. Pull the current blueprint — it does not create a database. |
| Apply succeeds but the API logs a connection error | `DATABASE_URL` was pasted with a trailing space or truncated, or it is an *external* URL for a Render database that should use the internal one |
| API starts, dashboard loads, but every write 500s with a column error | Table-name collision: `DATABASE_URL` points at a database that already had a `tasks`, `episodes` or `steps` table. See step 1, Option B. |
| Dashboard shows "Could not load the results" | Backend asleep (wait and reload) or `NEXT_PUBLIC_API_URL` is wrong |
| Browser console shows a CORS error | `FRONTEND_ORIGIN` on `agentgym-api` does not exactly match the dashboard's URL |
| Backend will not start, logs mention `INGEST_API_KEY` | `ENV=prod` with the key still set to `dev-key` |
| Upload returns 401 | `--key` does not match `INGEST_API_KEY` on Render |
| Upload returns 400 saying "unknown task" | Run `sync-tasks` before uploading episodes |
| Dashboard builds but shows no data after a redeploy | `NEXT_PUBLIC_API_URL` is read at build time; changing it needs a redeploy, not a restart |
| Everything 404s, or the data vanished after a month | The free Postgres expired. See the table above. |

The backend rewrites a `postgres://` or `postgresql://` prefix to
`postgresql+psycopg://` for you, so a connection string from any provider can
be pasted exactly as given.

## Costs

All three free tiers are enough for this project: the database is a few hundred
kilobytes, the API serves a handful of requests, and the dashboard is mostly
static. The LLM agent runs on your machine, not on Render, and the evaluation in
the README was done entirely within Google's Gemini free tier.

## Deploying somewhere else

The blueprint is a convenience, not a requirement. Both services are ordinary
apps — an ASGI app and a Next.js app — so any host works. You need:

- **Backend**: `pip install -r backend/requirements.txt`, then
  `uvicorn app.main:app --host 0.0.0.0 --port $PORT` with `backend` as the
  working directory. Set `DATABASE_URL`, `INGEST_API_KEY`, `FRONTEND_ORIGIN`
  and `ENV=prod`.
- **Frontend**: `npm ci && npm run build`, then `npx next start -p $PORT` with
  `frontend` as the working directory, and `NEXT_PUBLIC_API_URL` set at build
  time.
- **Database**: any Postgres. Leave `DATABASE_URL` unset to fall back to local
  SQLite.
